# 과목 노트 업데이트는 LangGraph Postgres 체크포인터로 재개하고, 의미 충돌은 interrupt로 사용자 확인을 받는다

ADR-0009(2026-11-18 변경)는 체크포인터를 빼고 단계 완료 기록(`note_updates.completed_stages`)으로 재개하기로 했다. 그런데 이렇게 하면 SFR-008 4)의 "의미 충돌은 사용자 확인을 받는다"를 그래프 밖에서 따로 이어 붙여야 한다. 단원별 병합을 재개하려면 단원마다 완료 기록을 남겨야 하고, 그 단원 경계도 따로 저장해야 한다. 이 서비스는 AI 에이전트 과제라서 사람이 판단에 끼어드는 흐름(human-in-the-loop)을 LangGraph로 실제로 보여 줘야 한다. 그래서 과목 노트 업데이트 그래프에는 Postgres 체크포인터(`langgraph-checkpoint-postgres`)를 쓴다. 그래프는 입력 → 배치 → 단원별 병합 → 충돌 분류 → 반영 순서로 돈다. 단원별 병합은 `Send`로 단원마다 병렬 실행하고, 의미 충돌이 있으면 `interrupt`로 멈춘다. 멈추면 작업은 끝나고, 사용자가 결정한 뒤 재개 작업이 같은 thread를 `Command(resume=...)`로 이어 간다. MVP부터 이렇게 한다. Q&A 그래프는 SER-001 4)("Q&A 생성 도중의 데이터는 영구 저장하지 않는다") 때문에 계속 체크포인터 없이 메모리에서만 돈다. 대화는 `messages` 테이블로 기억한다.

## Consequences

- ADR-0009가 체크포인터를 뺀 이유인 이중 반영(노트 반영과 체크포인트 저장이 서로 다른 트랜잭션)은 부작용이 있는 노드를 충돌 저장 노드와 반영 노드 둘로 좁혀 막는다(2026-11-19 변경). 배치·병합·분류는 결과를 그래프 상태에만 두므로 다시 돌아도 LLM 비용만 든다. 충돌 저장 노드는 이 `note_update_id`의 변경안이 이미 있으면 건너뛴다. `interrupt()`만 하는 노드는 따로 두고 아무것도 저장하지 않는다. LangGraph는 재개할 때 `interrupt()`를 부른 노드를 처음부터 다시 실행하므로, 한 노드에서 저장과 `interrupt()`를 함께 하면 재개할 때마다 같은 충돌이 다시 저장된다. 반영 노드는 노트 변경과 `note_updates.status = 'completed'`를 한 트랜잭션으로 커밋하고, 이미 `completed`면 건너뛴다. 그래서 `note_updates.completed_stages`는 두지 않는다.
- 단원은 과목 노트의 최상위 제목 블록 하나와 다음 최상위 제목 앞까지의 블록이고, 그 제목 블록 ID로 식별한다. 배치 단계에서 LLM이 새 강의 블록마다 기존 단원 ID 또는 새 단원(서버가 미리 발급한 UUIDv7)을 정한다. 이 배치 계획은 그래프 상태로 체크포인트에 남으므로, 재개해도 단원을 다시 나누지 않는다. 끝난 단원의 병합 결과도 체크포인트에 남아 다시 하지 않는다. `Send`는 그래프 순환이 아니므로 `recursion_limit`에 걸리지 않는다.
- 사용자 확인을 기다리는 동안 `note_updates.status`는 `awaiting_user`다. 이 값은 그래프가 interrupt로 멈춰 실행이 돌아온 뒤(체크포인트 저장 뒤) 처리 함수가 쓴다(2026-11-19 변경). 체크포인트보다 먼저 보이면 그사이 들어온 결정으로 재개할 interrupt가 없다. 결정 API는 `note_updates` 행을 `FOR UPDATE`로 잠그고 결정 저장·남은 `pending` 세기·재개 작업 등록을 한 트랜잭션에서 하고, 결정 저장이 실제로 `pending` 행을 바꾼 요청만 재개를 등록한다. 대기·실행 중인 재개 작업은 업데이트당 하나다(`jobs_one_course_update`). 그래서 마지막 결정이 동시에 들어오거나 다시 전송돼도, [재시도]를 연타해도 재개는 한 번이다. 재개·재시도 작업은 thread에 남은 interrupt가 있으면 `Command(resume=...)`로, 없으면 마지막 체크포인트부터 이어 간다. 마지막 결정 직후 워커가 죽어도 재시도가 저장된 결정으로 같은 interrupt를 이어 간다. 확인할 충돌은 `note_changes(status='pending', note_update_id)`에 두고, 화면은 이 행을 읽는다. 체크포인트는 읽지 않는다. 사용자는 충돌마다 수락(`accepted`)하거나 거절(`rejected`)하고, `pending`이 0개가 되면 재개 작업이 들어간다. 반영 노드는 결정을 `note_changes`에서 읽어 `accepted`를 반영한다. 그사이 Q&A 반영은 '과목 노트 업데이트 중'으로 보고 대기시킨다(SFR-020 5). 새 강의 업데이트는 대기 요청 하나로 합친다.
- MVP에는 편집 잠금(SFR-008 5, QUR-002 3)이 없어서 업데이트 도중에도 사용자가 블록을 고칠 수 있다(2026-11-19 변경). 그래서 재개할 때 충돌 분류로 되돌아가지 않고, 반영 노드가 바꿀 블록마다 판단할 때 본 `revision`(그래프 상태, 충돌은 `note_changes.base_revision`)을 지금 값과 비교한다(ADR-0006). 다르면 그 변경은 반영하지 않고 `held`와 이유로 남기며, 사용자가 화면에서 AI 제안을 보고 직접 반영한다. 되돌아가는 길을 만들면 다시 병합하는 동안 또 편집이 생길 때마다 흐름이 반복되고, 의미 충돌이 나면 사용자 확인 대기로 다시 들어가야 한다.
- 일시정지는 노드 사이에서 `paused`를 확인해 멈추고, 같은 thread로 이어 간다. 취소는 `cancelled`로 바꾸고 thread를 지운다. 늦게 끝난 실행의 결과는 반영 노드가 상태를 확인해 버린다.
- 작업이 실패하면(예외, 회수 루프의 `stalled` 처리) 실패 훅이 `note_updates`를 `failed`로 바꾸고 thread는 남긴다(2026-11-19 변경). `failed`는 '실패 후 재개 대기'(SFR-008 비고)라 그동안 대기 요청은 시작하지 않는다. 재시도는 같은 `note_updates` 행·같은 thread를 새 작업으로 이어 가, 끝난 단원을 다시 병합하지 않는다(SFR-043 2). 체크포인트는 노드가 끝날 때만 쓰이므로 마지막 체크포인트는 끝난 노드까지의 상태이고, 멈춘 줄 알았던 옛 실행이 늦게 써도 데이터는 반영 노드의 `completed` 확인이 지킨다. 취소하면 `cancelled`로 바꾸고 thread를 지운다.
- 체크포인트 테이블은 별도 스키마 `langgraph`에 두고 `thread_id`는 `note_updates.id`다. 테이블에 `user_id`가 없어 RLS를 받지 않는다. 그래서 worker만 이 테이블을 쓰고, 업데이트가 완료·취소되면 thread를 지운다. 노트 삭제와 탈퇴 때는 cron이 함께 지운다. cron은 하루 한 번 `note_updates` 행이 없거나 `completed`·`cancelled`인 thread도 지운다. 지운 직후 늦게 끝난 노드가 체크포인트를 다시 쓰는 경우를 여기서 정리한다. 담기는 내용은 노트와 강의 내용이고 질문 원문이 아니므로 SER-001에 걸리지 않는다.
- 테이블은 worker가 시작할 때 `setup()`으로 만든다. 그래서 앱 계정에 `langgraph` 스키마의 생성 권한만 준다. `public` 스키마 권한은 그대로다.
- 인계(ADR-0018)를 넣으면 늦게 깨어난 실행이 체크포인트를 더 쓸 수 있다. 데이터는 반영 노드의 `attempt_no` 확인이 지키고, 체크포인트가 어긋나면 LLM 단계를 다시 할 뿐이다.
- 요구사항 COR-002 3)의 "LangGraph 체크포인터는 쓰지 않고, 과목 노트 업데이트는 DB의 단계 완료 기록으로 재개한다"를 이 결정에 맞춰 고친다.
