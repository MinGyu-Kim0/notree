# 작업 전달은 Taskiq와 RedisStreamBroker로 하고, 재시도는 OpenAI SDK에만 맡긴다

ADR-0001은 Redis Streams 위에 asyncio 워커를 직접 만들기로 했다. 그러면 소비 루프, 동시 실행 수 제한, 종료 처리, 멈춘 소비자의 메시지 회수를 모두 만들어야 한다. 이 부분은 Taskiq와 taskiq-redis의 `RedisStreamBroker`에 맡긴다. Redis Streams는 그대로라서 ADR-0001이 Redis를 고른 이유와 ADR-0005의 이벤트 Stream은 유지된다. 라이브러리가 해 주지 않는 것은 Notree가 만든다. 늦은 실행 차단은 [ADR-0018](0018-db-fencing-redis-lease.md), DB 커밋 뒤 ACK와 전달 누락 복구는 [ADR-0019](0019-outbox-and-ack-after-commit.md), 반영 시 근거 확인은 [ADR-0006](0006-commit-time-evidence-check.md)에 있다.

재시도도 직접 만들지 않는다. QUR-004 4)는 외부 호출 하나당 최대 4회(최초 + 재시도 3회, 내부 재시도 포함)이고, 인증 오류·잘못된 요청·정책 거절·사용자 취소는 재시도하지 않는다. OpenAI SDK는 `max_retries`를 주면 연결 실패와 408·409·429·5xx만 백오프와 `Retry-After`를 지키며 재시도하고, 400·401·403은 바로 실패시킨다. 그래서 `max_retries`를 3 이하로 두면 이 조항과 SIR-002(제공사 대기 시간 준수)를 그대로 충족한다. Taskiq 재시도 미들웨어까지 켜면 작업 재실행과 호출 재시도가 곱해져 호출 수가 상한을 넘으므로 쓰지 않는다.

## Consequences

- 작업을 처음부터 다시 실행하는 건 워커가 죽어 다른 워커가 인계받을 때뿐이다. 인계는 `jobs.attempt_no`를 올리고(ADR-0018), 3을 넘으면 작업을 실패로 끝낸다. 같은 작업이 계속 워커를 죽이는 경우를 막는다. 인계된 작업은 완료 기록이 있는 단계 다음부터 이어 간다.
- 호출마다 timeout을 정한다(SDK 기본값은 10분). SDK가 재시도하며 기다리는 동안에도 lease heartbeat는 별도 태스크로 돈다.
- Soniox 재연결(1·2·4초 간격 3회, QUR-003)도 같은 '호출 하나당 4회' 기준이다.
- Q&A가 긴 배경 작업(최종 노트, 과목 노트 업데이트, 출제)에 밀리지 않도록 Q&A와 배경 작업을 다른 Stream으로 보내고, 워커 동시 실행 수를 따로 둔다. 수치는 부하 측정 뒤 정한다.
- ACK는 작업 함수가 도메인 커밋까지 마치고 반환한 뒤에 한다(`ack_type=when_executed`). 고정할 패키지 버전에서 이 설정과 회수 동작이 문서대로인지 PoC로 확인한다. 다르면 이 ADR을 다시 연다.
- 요구사항 v0.4.4에서 QUR-004 4)의 '작업 하나당'을 '외부 호출 하나당'으로 고쳤다.
- `max_retries`는 3보다 낮게 둔다(2026-11-18 변경). 초기값은 배경 작업 2, Q&A(`qa_answer` 작업의 모든 단계, 2026-11-19 변경) 1이다. QUR-004 4)는 인계를 재시도와 따로 세므로 3이어도 요구사항 위반은 아니다. 하지만 최악이면 같은 호출이 인계 3회 × 4회 = 12번 나가 장애 때 비용이 커지고, Q&A 답변은 90초(PER-004 4) 안에 백오프를 여러 번 기다릴 여유가 없다. 호출 timeout은 작업 마감까지 남은 시간 안에서 정하고, 최악의 비용은 비용 예약 한도(PER-003 2)가 막는다. 외부 호출 횟수를 세는 DB 테이블은 만들지 않는다.
