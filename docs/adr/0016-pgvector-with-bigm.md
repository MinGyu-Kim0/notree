# 의미 검색은 별도 벡터 DB가 아니라 pgvector로 하고, pg_bigm 키워드 검색과 함께 쓴다

Q&A 근거 검색에 의미 검색을 쓰기로 했다. 별도 벡터 DB(Pinecone, Qdrant, Chroma 등)를 두면 RLS가 없어 사용자 경계를 앱 필터 하나에 맡기게 되고(SER-002 3), 휴지통 이동·복원·영구 삭제를 따로 동기화해야 하며(DAR-006 1, ADR-0011), 사용 시점 재확인(DAR-005 1)이 DB 두 곳을 오가고, 백업과 삭제 기록 재적용(DAR-007)도 따로 해야 한다. EC2 한 대 구성(ADR-0004)에 컨테이너가 늘거나, SaaS면 COR-005 위탁 대상이 늘어난다. 개인 규모(사용자당 블록 수천~수만 개)에서는 PostgreSQL 확장 pgvector의 HNSW 인덱스로 충분하다. 그래서 벡터를 기존 `search_entries` 행에 키워드용 본문과 같이 둔다. 키워드 검색(pg_bigm)은 빼지 않는다. SFR-047 노트 검색은 요구사항 문구가 '키워드로'이고, 전문용어·약어·코드 식별자는 벡터 검색이 놓치기 쉽다. pg_trgm은 3글자 단위라 두 글자 한국어 검색어에 약해 쓰지 않는다.

## Consequences

- 임베딩 모델은 OpenAI `text-embedding-3-small`이다. `search_entries`에 `embedding vector(1536)`(이 모델의 기본 차원)과 `embedding_model`을 두고 HNSW 인덱스를 건다. 모델이나 차원을 바꾸면 열 타입과 인덱스를 바꾸고 전부 다시 만든다(DAR-005 3).
- 한 행에 키워드 본문과 벡터가 같이 있어서, 삭제·갱신·휴지통 처리 때 둘이 어긋나지 않고 RLS도 그대로 적용된다.
- Q&A 검색은 bigm 결과와 벡터 결과를 합친다(예: 순위 역수 합). 노트 검색 화면(SFR-047)은 키워드 결과를 기본으로 보여 준다.
- 임베딩은 OpenAI API로 만든다. OpenAI는 이미 위탁 대상이라 COR-005 고지 대상은 늘지 않지만, 노트와 전사 본문이 임베딩 호출로 나간다는 점을 고지 항목에 넣는다. 임베딩 비용은 비용 예약(PER-003)과 `ai_calls`에 포함한다.
- 검색 자료 갱신 작업이 키워드 본문과 벡터를 함께 다시 만든다. 벡터 생성이 실패해도 키워드 검색은 동작하고, 갱신 중·실패 상태는 작업 상태로 구분한다(DAR-005 2).
