# 늦은 실행은 DB 실행 시도 번호로 막고, Redis lease는 중복 실행을 줄이는 데만 쓴다

워커가 GC나 네트워크 지연으로 멈췄다 깨어나거나 lease가 만료된 뒤에도 돌고 있으면, 같은 작업을 두 실행이 동시에 한다. Redis lease만으로는 이걸 막을 수 없다. 키가 만료되거나 Redis 재시작으로 사라지면 두 실행이 모두 자기가 주인이라고 믿는다. 반대로 lease를 DB에만 두면 heartbeat가 전부 DB 쓰기가 되고, 장애 감지를 빠르게 하려고 간격을 줄일수록 쓰기가 늘어난다. 그래서 역할을 나눈다. 정확성은 DB가 맡는다. 실행을 시작하거나 인계받을 때 `UPDATE jobs SET attempt_no = attempt_no + 1 WHERE id = ? RETURNING attempt_no`로 번호를 받고, 노트·답변·관찰·단계 완료 기록 등 모든 결과 반영 트랜잭션에서 그 작업 행의 `attempt_no`가 내 번호인지 확인한다. 다르면 반영하지 않는다. 효율은 Redis가 맡는다. `SET lease:{job_id} {소유자 토큰} NX PX 30000`으로 lease를 잡고, 10초마다 값이 내 토큰일 때만 연장한다(Lua). 끝나면 같은 조건으로 지운다.

## Consequences

- 실행 시작 순서는 Redis lease 획득 → DB 번호 발급이다. 순서가 반대면 lease를 못 잡은 워커가 번호만 올려서, 정상 실행 중인 작업을 차단해 버린다.
- 재전달된 메시지는 lease가 살아 있으면 바로 ACK하고 끝낸다. 다른 실행이 처리 중이라는 뜻이다. `jobs`가 이미 끝난 상태여도 ACK만 한다.
- Redis가 무엇을 잃어도 최악은 LLM 중복 호출 비용이다. 데이터는 DB 번호 확인이 지킨다. Redis 장애 중에는 새 실행과 인계가 lease를 못 잡아 보류된다. 이미 도는 작업은 끝까지 가도 안전하다. 그동안 인계될 수 없고, 쓰기는 DB가 막기 때문이다.
- 과목 노트 편집 잠금(QUR-002)은 사용자에게 보이는 정확성이라 DB `notes.locked_until`에 둔다. 과목 노트 업데이트 작업이 20초마다 60초 뒤로 연장하고, 이 연장도 `attempt_no`를 확인한다. 워커가 죽으면 60초 안에 풀린다.
- `attempt_no`(늦은 실행), 대상 세대 번호(취소·삭제, ADR-0006), 노트 버전(다른 변경과의 충돌)은 서로 다른 문제를 막는 별개의 값이다. 하나로 합치지 않는다.
- TTL 30초, heartbeat 10초는 초기값이다.
